# pdf-to-epub

Native macOS app that converts scanned documents (a PDF or a folder of page images)
into EPUB 3, reproducing the document's formatting as faithfully as possible:
headings, paragraphs, illustrations with captions, and footnotes.

Status: **document model and EPUB export implemented** in `Packages/ScanCore`
(`DocumentModel`, `EPUBExport`), with tests. `App/` is a placeholder SwiftUI
shell. Nothing reads page images yet. Modules listed below that do not exist
yet are the agreed target, created when a test first needs them.

## Product decisions

| Topic | Decision |
|---|---|
| Platform | macOS 26+ only. Cross-platform is not a goal. |
| Stack | Swift 6 (strict concurrency), SwiftUI, Swift Testing. |
| OCR engine | Apple Vision only. Free, on-device, no network calls, no paid services. |
| Document languages | Ukrainian, English, and Ukrainian with English fragments on the same page. |
| Document types (v1) | Fiction and non-fiction with footnotes, illustrations, multi-level headings, lists. |
| Out of scope (v1) | Tables, multi-column layout, math formulas, verse line preservation, LLM-based correction. |
| Distribution | Personal / open-source build. No App Store, no sandbox requirement. |
| Output | EPUB 3 that passes `epubcheck` with no errors. |

### What the input really looks like

The user's sample sets (`/Users/mac/scans_test`, four sets, ~850 PNG pages)
are **clean pages of a clean-page source**, not paper scans: clean text, no skew, no
running headers, a page number at the bottom, note references as blue links,
notes collected at the end of the document, illustrations with captions, a cover
and a contents page. Design for this first; paper scans are a later case.

These documents are commercial material. Never copy their pages or text into the
repository, tests, docs, or commit messages. Tests that need them read the
folder from the `PAGESCAN_SAMPLES_DIR` environment variable and are skipped
when it is unset. Committed fixtures are synthetic pages generated by code.

Do not add a dependency, a network call, or an out-of-scope feature without
asking the user first.

## Architecture

A pipeline of independent stages. Each stage is a pure transformation behind a
protocol, so it can be tested alone and replaced with a fake.

```
Import -> Preprocess -> OCR -> Layout analysis -> Document model -> EPUB export
                                                        ^
                                                  user review (UI)
```

1. **Import** - PDF (PDFKit) or image folder becomes an ordered list of pages.
2. **Preprocess** - deskew, crop margins, split a two-page spread into pages.
3. **OCR** - `RecognizeDocumentsRequest` with explicit languages. We use only
   its lines and word boxes; its paragraph grouping, `title`, and confidence
   proved unreliable (ADR 0001). The first request in a process takes over a
   minute to load the model, so warm it up in the background.
4. **Layout analysis** - classifies blocks. Vision does not know what a heading
   or footnote is, so this is heuristic:
   - headings: line height relative to body text, centering, surrounding space;
   - paragraphs: built from line geometry (indent, vertical gap), continued
     across pages when a page starts with an unindented line;
   - notes: references found by link colour in the page image and re-recognised
     as a cropped region; note bodies are endnotes at the end of the document or
     footnotes at the page bottom;
   - running headers/footers and page numbers: repetition across pages, removed;
   - illustrations: non-text regions cropped out as images, captions attached;
   - hyphenated words and paragraphs broken across lines/pages are rejoined.
5. **Document model** - chapters, headings, paragraphs, footnotes, images.
   This is the single source of truth: the UI edits it, the exporter reads it.
6. **EPUB export** - semantic XHTML, navigation document (TOC), pop-up
   footnotes (`epub:type="noteref"` / `"footnote"`), embedded images, metadata.

### User involvement (human in the loop)

OCR and layout heuristics will be wrong sometimes; the app is built around
making corrections cheap rather than pretending they are not needed.

- **Review screen**: page scan next to the recognized result; suspicious words
  highlighted (`NSSpellChecker`, mixed-script and digit/letter confusion rules;
  Vision confidence is only a tie-breaker); "next issue" navigation.
- **Structure fixes**: change a block's type (heading level / paragraph /
  footnote / illustration / ignore), redraw a region, merge or split blocks.
- **Propagation**: a correction to one block's type can be applied to
  similar-looking blocks across the document, with the user's confirmation.
- **Persistent project**: work is saved to disk as a project bundle so a long
  document can be reviewed across sessions. User corrections are stored separately
  from OCR output and must survive a re-run of OCR or layout analysis.

### Module layout (target)

```
Packages/ScanCore/          Swift package, no UI imports
  Sources/
    DocumentModel/          value types; no dependencies
    Importing/              PDF and image folder import
    Preprocessing/          deskew, crop, spread splitting
    OCR/                    Vision adapter behind OCREngine protocol
    LayoutAnalysis/         block classification heuristics
    EPUBExport/             EPUB 3 writer
    ProjectStore/           project bundle persistence
    pagescan/               CLI for batch conversion and debugging
  Tests/                    one test target per module + Fixtures/
App/                        SwiftUI app (thin: views + view models)
docs/                       feature and architecture documentation
```

Rules:
- `ScanCore` never imports SwiftUI or AppKit UI types. The app depends on the
  package, never the reverse.
- Only `OCR` imports Vision; only `Importing` imports PDFKit. Everything else
  works on the package's own value types.
- `DocumentModel` types are `Sendable`, `Codable` value types.

## Development process

### TDD (mandatory)

Red -> green -> refactor, for every change in behavior:

1. Write a failing test that states the behavior. Run it and see it fail for
   the right reason.
2. Write the minimum code to pass.
3. Refactor with tests green.

No production code without a test that required it. A bug fix starts with a
test that reproduces the bug.

Testing approach per layer:
- **Pure logic** (layout heuristics, hyphen joining, footnote matching, EPUB
  XHTML generation): unit tests over hand-built input values. Vision is never
  called in these tests.
- **Vision adapter**: a small number of integration tests against fixture
  images, asserting on tolerant properties (contains text, block count), since
  OCR output can change between OS releases.
- **Golden pages**: `Tests/Fixtures/` holds real scanned pages with the
  expected document structure. These are the regression suite for layout
  heuristics; every heuristic change runs against all of them. Fixtures must be
  public-domain or the user's own scans.
- **EPUB export**: structural assertions on the generated package, plus
  `epubcheck` validation as an integration test.
- **UI**: logic lives in view models, which are unit tested. Views stay thin.

### Commands (once scaffolded)

```bash
swift test --package-path Packages/ScanCore            # all core tests
swift test --package-path Packages/ScanCore --filter LayoutAnalysisTests
xcodebuild -project App/PDFToEPUB.xcodeproj -scheme PDFToEPUB build
swiftformat . && swiftlint                             # before every commit
```

`epubcheck` is installed (Homebrew). Still to install: `swiftlint`, `swiftformat`.

### Code standards

- Swift 6 language mode, strict concurrency, warnings treated as errors.
- Follow the Swift API Design Guidelines. SwiftFormat and SwiftLint are the
  arbiters of style; do not hand-argue formatting.
- Dependency injection through protocols and initializers; no singletons, no
  global mutable state.
- Typed errors per module; never `try!`, `fatalError`, or force-unwrap in
  production code.
- Heavy work (OCR, image processing) runs off the main actor, reports
  progress, and supports cancellation.
- ZIP output uses the in-house `ZipWriter` (Foundation has no ZIP API).
- Prefer Apple frameworks. A third-party dependency needs a stated reason and
  the user's approval.
- Small, focused commits in Conventional Commits format (`feat:`, `fix:`,
  `test:`, `docs:`, `refactor:`).

### Language

- Code, comments, commit messages, and documentation: **English**.
- Conversation with the user: **Ukrainian**.
- App UI strings: localizable from the start (String Catalog), English base
  with Ukrainian localization.

### Documentation (mandatory)

- Every public type and function has a DocC comment explaining what it is for
  and any non-obvious behavior. Comments explain *why*, not *what*.
- Every user-facing feature has a page in `docs/features/` describing what it
  does, how to use it, and its known limits. A feature is not done until its
  page exists and is linked from `docs/README.md`.
- Significant design choices are recorded as short ADRs in `docs/adr/`.
- `README.md` covers build, run, and a usage walkthrough.

### Definition of done

1. Tests were written first and pass; the full suite is green.
2. SwiftFormat and SwiftLint are clean; no compiler warnings.
3. Public API has DocC comments; the feature page in `docs/features/` is
   written or updated.
4. For UI changes: the app was launched and the change was checked by hand.
